# 재생 Esc 접근성 수정 및 서버 복구 (2026-10-07)

## 확인된 결함과 수정

GUI 재검증에서 재생 클릭 후 포커스가 바깥 기록 컨테이너로 이동하면 Esc가 동작하지 않는 현상이 보고됐다. 기존 keydown 처리의 첫 조건은 내부 .playback 요소에 포커스가 없으면 모든 키를 무시했다. 이 조건 때문에 바깥 컨테이너에서 발생한 Esc도 종료 함수에 도달하지 못했다. Safari가 포커스를 이동시킨 원인 자체는 이번 코드 검사만으로 확정하지 않는다.

재생 모드가 열려 있는 동안 문서 수준에서 Esc를 처리하도록 변경했다. 화살표·Home/End 탐색은 기존처럼 내부 재생 영역에 한정한다. 재생 전·진행 중·일시정지·종료 시점 모두 Esc로 같은 종료 경로를 호출하며 모드 종료 후에는 Esc를 가로채지 않는다. 컴포넌트 해제 시 이벤트 리스너를 제거한다. 재생 버튼의 텍스트를 매 100ms 불필요하게 다시 만들지 않고 실제 변경 시만 갱신하며, 재생/일시정지 클릭 후 해당 버튼 포커스를 유지한다.

## 검사

- npm test: 60개 통과. 새 4개 회귀검사는 진행 중 바깥 컨테이너 포커스에서 Esc로 종료·시간 정지, 재생 전/일시정지/완료/재진입, 내부에 한정된 방향키 탐색, 비활성/이미 처리된 이벤트/리스너 해제 동작을 검증한다.
- npm run check: 전체 JavaScript 구문 검사 통과.
- 부모가 전달한 GUI 통과: 새로고침 없이 오른쪽 추정·양쪽 탭 복귀 동기화, 396프레임/119.6초 기록, 미리 재생과 종료 버튼 복귀. 이 결과는 이번 Esc 수정 후의 GUI 통과가 아니다.
- 사용자가 화면을 조작 중이고 브라우저에 기록이 남아 있어 이번 작업에서는 Safari 조작·새로고침·시연 초기화·기록 변경을 하지 않았다. 새 Esc 코드의 실제 Safari 동작은 남은 재검증이다.

## 서버 중단 조사 및 복구

기존 실행 세션 79628은 Unknown process id를 반환했고, 4173/4174 HTTP는 Connection refused, 해당 포트의 리스너는 없었다. 확보된 애플리케이션 종료 로그가 없어 종료 신호·충돌·실행 환경 정리 중 무엇인지 확정할 수 없다. 앞서 exec-server 연결 단절이 있었지만 이번 종료의 직접 원인으로 단정하지 않는다.

기존 원본 npm run dev를 수동 실행하되 stdin을 분리하고 별도 프로세스 세션에서 실행해 터미널 연결 종료 영향을 줄였다. 출력과 오류는 작업공간 seat-care-local-server.log, 실행 정보는 seat-care-local-server-process.json에 보존한다. launchd/자동 시작 등록·보안 설정은 변경하지 않았다. 재부팅/실행 환경 정리에도 영구 유지된다고 보장하지 않는다. 서버 종료로 이미 사라진 서버 메모리 기록은 복구했다고 주장하지 않는다. 브라우저에 남아 있는 119.6초 기록은 조작하지 않았다.

## 재검증 시 주의

원본 파일 적용은 기존 탭에 이미 로드된 JavaScript를 교체하지 않는다. 기존 탭의 119.6초 기록을 먼저 저장한 뒤 별도 탭 또는 새로 로드한 화면에서 재생 → 바깥 컨테이너 포커스 → Esc를 확인해야 한다. 이번 작업에서 새로고침하지 않았다.

## 보존

변경 전 원본은 seat-care-before-escape-fix에 백업했다. 전체 SHA256 manifest로 원본 변경을 감지하고 변경 파일만 적용한다. coin PID 90721/세션 45555를 포함한 다른 프로세스·폴더·포트는 건드리지 않았다.
